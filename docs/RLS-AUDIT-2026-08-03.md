# Applied — live RLS audit, 2026-08-03

Read against the production Supabase database, not against the migrations.

## The claim holds

All eight tenant tables carry `ENABLE` + `FORCE ROW LEVEL SECURITY` and four
policies each:

`applications` · `contacts` · `email_embeddings` · `emails` · `interviews` ·
`sync_state` · `training_data` · `user_credentials`

`FORCE` matters here: without it, policies do not apply to the table owner, and
the owner is what the application usually connects as.

## Two findings — BOTH FIXED 2026-08-03

### 1. `alembic_version` has RLS ENABLED with ZERO policies and no FORCE

A table with RLS on and no policy denies everything to any role that does not
bypass RLS. Today the app connects as a `BYPASSRLS` role, so nothing is broken
and this is latent rather than live.

It stops being latent the moment migrations run as a non-bypassing role -- which
is exactly the hardening Cadence just completed. Alembic would read the version
table, get **zero rows**, conclude the database is unmigrated, and attempt to
replay every migration from the beginning against a populated database.

That failure is silent at the point of reading and destructive at the point of
writing, which is the worst combination. Fix before, not after, any move to a
non-superuser application role.

### 2. `anon` holds table grants on all nine tables

Not currently exploitable: RLS is forced and the policies key on the
authenticated user, so `anon` matches no rows. It is unnecessary surface all the
same, and it is one `DISABLE ROW LEVEL SECURITY` away from being live. Cadence
had the identical grant set and it was revoked there.

Verify how the frontend talks to Supabase before revoking. If anything uses the
publishable/anon key through PostgREST, revoking breaks it; if all access is
through the FastAPI backend's own connection, the grants are dead weight.

## Resolution

Both fixed the same day, in migration `revoke_anon_grants_and_fix_alembic_version_rls`.

Verified after applying:

- all nine tables now show no `anon` or `authenticated` entry in `relacl`;
- `alembic_version` is `rls = false`, so a non-bypassing Alembic reads its real
  head (`c4user_creds_rls`) instead of zero rows;
- the eight tenant tables are untouched: `rls = true, forced = true,
  policies = 4`;
- application data intact -- 20 applications, 39 emails.

The revoke was safe because it was checked before it was run: nothing in the 550
tracked files uses `supabase-js`, `createClient()` or an anon key, so there was
no caller to break.

Both findings came from reading `pg_class` and `pg_policy` directly rather than
trusting the migration history -- the same method that caught the
constraint-versus-index bug in Cadence on the same day, and the one thing that
worked reliably all day.

## Third finding, and it is the significant one: the RLS is INERT

Found after the first two were fixed, by reading the policy predicates rather
than the policy count.

Every policy on every tenant table keys on **`auth.uid()`**:

```sql
applications_select  USING      (user_id = auth.uid())
applications_insert  WITH CHECK (user_id = auth.uid())
applications_update  USING/CHECK (user_id = auth.uid())
applications_delete  USING      (user_id = auth.uid())
```

`auth.uid()` is Supabase Auth's function. It reads the `request.jwt.claims`
GUC, and **PostgREST is what sets that GUC**. Applied's backend is FastAPI over
asyncpg -- a direct connection. Nothing in the 550 tracked files sets
`request.jwt.claims`, `set_config`, or `SET LOCAL`.

So the policies are inert for the real access path, for two independent reasons:

1. the backend connects as a role with `BYPASSRLS`, so policies are never
   consulted; and
2. even without that, `auth.uid()` would return NULL on a direct connection, and
   `user_id = NULL` is never true -- so **every policy would deny everything**.

The second is worse than the first. Removing the bypass -- the exact hardening
Cadence just completed -- would not turn RLS on here. It would take the
application down, and it would do so by returning **zero rows rather than
raising**, so it would look like total data loss rather than a permissions
error.

### Why the 10 RLS tests pass anyway

`backend/tests/test_rls_postgres.py` builds its own Supabase-shaped `auth`
schema, defines `auth.uid()` itself, and sets `request.jwt.claims` per
transaction:

```
CREATE OR REPLACE FUNCTION auth.uid() RETURNS uuid ...
  current_setting('request.jwt.claims', true)::jsonb ->> 'sub'
```

It then creates the policies and asserts they isolate. They do. What the suite
proves is that **the policy shape is correct** -- and it proves it inside an
environment the suite constructs and production does not have.

This is the same failure as Cadence's constraint-versus-index bug on the same
day: a fixture faithful to the intent rather than to the deployment. Cadence's
version cost four tags and an hour of downtime. This one has cost nothing yet
because nobody has removed the bypass.

### What Applied actually needs

Pick one, and do not do the Cadence cutover before it:

- **Bind identity on the connection.** Wrap each request the way Cadence's
  `runWithRls` does: `BEGIN`, set the claim (`set_config('request.jwt.claims',
  ...)` to keep `auth.uid()` working, or repoint the policies at a plainer GUC
  such as `app.user_id`), statement, `COMMIT`, on one dedicated pooled client.
  Then move to a `NOBYPASSRLS` role.
- **Or state plainly that isolation is enforced in the application layer**, and
  that the policies are defence-in-depth staged for a future cutover.

Until one of those is true, the accurate claim is that the policies are written
and machine-checked, not that the database is enforcing them.
